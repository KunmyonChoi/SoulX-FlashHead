# 음성 에이전트 프레임워크 v2: 요구사항 문서 (PRD)

작성일 2026-11-17. 이 문서는 무엇을 만들지와 왜 만드는지를 정한다. 어떻게 만드는지는 `ARCHITECTURE.md`, 누가 언제 만드는지는 `PLAN.md`에 있다.

## 1. 배경

v1(`realtime_mic_app.py`, `realtime_tools.py`, `realtime_mic_client.html`, `realtime_asr_server.py`)은 아바타 하나가 음성으로 대화하며 지식베이스, 날씨, 뉴스, 긱뉴스, 위키백과를 찾아 답하는 데모다. 잘 동작하지만 세 가지 한계가 있다.

- 에이전트의 성격(지시문, 도구 안내, 검사 규칙)이 코드에 박혀 있어 다른 업무의 에이전트를 만들려면 코드를 고쳐야 한다.
- 대화 기록이 화면에만 보이고 저장되지 않아, 끝난 대화를 되짚거나 고치기 전후를 비교할 수 없다.
- 도구가 모두 조회용이라, 주문·환불·예약처럼 무언가를 바꾸는 업무를 안전하게 처리할 장치가 없다.

v1은 그대로 두고 계속 실행할 수 있어야 한다. v2는 `v2/` 아래에 따로 만든다.

## 2. 목표와 범위

### 목표

여러 업무의 음성 에이전트를 **정의하고, 만들고, 시험하고, 승인을 거쳐 배포하고, 지켜보고, 원인을 가리고, 고치는** 전 과정을 한 환경에서 할 수 있게 한다.

### 확정된 결정

| 번호 | 결정 |
|---|---|
| D1 | 프레임워크를 먼저 정의하고, 대표 시나리오 하나(쇼핑몰 주문 문의)로 끝까지 검증한다 |
| D2 | 아바타는 옵션이다. 음성만 쓰는 대화가 기본이고, 채널이 요청할 때만 영상을 붙인다 |
| D3 | 제작 에이전트는 초안 작성, 시험, 수정안 제안까지 한다. 배포는 사람의 승인을 거친다 |
| D4 | 외부 시스템은 잘 정의된 연동 인터페이스 뒤에 두고, 지금은 더미로 구현한다 |
| D5 | 개인 민감정보를 저장하지 않는 구조로 한다. 보관 기한은 설정값으로 두어 법령에 맞춘다 |

### 범위 밖

- 실제 업무 시스템(주문, 예약, 병원) 연결. 인터페이스와 더미까지만 만든다.
- 전화망 연결. 채널 인터페이스는 두되 구현은 웹(글, 음성, 아바타)만 한다.
- 드라이브스루, 키오스크, 항공, 병원 에이전트의 완성. 정의서 형식이 이들을 담을 수 있는지만 확인한다.
- 법령 해석. 가리기 규칙과 보관 기한을 설정으로 제공하는 데까지다.

## 3. 사용자

| 사람 | 하는 일 |
|---|---|
| 업무 담당자 | 업무를 알지만 개발자는 아니다. 에이전트가 무엇을 해야 하는지 정하고, 배포를 승인한다 |
| 제작 에이전트 | 담당자와 대화하며 정의서를 만들고 고친다. 시험을 돌리고 비교표를 만든다 |
| 개발자 | 외부 시스템 연동 도구를 등록하고, 제작 에이전트가 못 푸는 문제를 푼다 |
| 운영자 | 배포하고, 지켜보고, 되돌린다 |
| 고객 | 에이전트와 글이나 음성으로 대화한다 |

## 4. 사용자 시나리오

각 시나리오 끝의 괄호는 관련 요구사항 번호다.

**S1. 말로 에이전트 초안을 만든다.** 담당자가 제작 에이전트에게 "주문 조회, 배송 상태, 환불 문의를 받는 상담원"을 설명한다. 제작 에이전트가 본인 확인 방법, 환불 처리 범위, 사람에게 넘기는 조건을 되묻고, 정의서 초안을 만든다. 담당자는 정의서 파일을 직접 고치지 않고 "환불 금액이 10만 원을 넘으면 사람에게 넘겨"처럼 말로 고친다. (R-DEF-1~5, R-BLD-1~3)

**S2. 외부 시스템에 연결한다.** 개발자가 주문 시스템 API를 도구 계약서로 등록한다. 조회와 변경을 구분하고, 변경 도구에는 실행 전 확인 문장과 중복 방지 키를 적는다. 실제 시스템 대신 쓸 더미를 함께 둔다. (R-TOOL-1~8)

**S3. 가상의 고객으로 시험한다.** 여러 성향의 가상 고객(빨리 말하는 사람, 중간에 말을 바꾸는 사람, 본인 확인을 건너뛰려는 사람)이 에이전트와 대화한다. 끝나면 성공 기준 통과율과 실패한 대화가 나온다. (R-EVAL-4~7)

**S4. 채널에 맞춰 배포한다.** 같은 정의서가 글 채널, 음성 채널, 아바타 채널로 나간다. 새 버전은 일부 대화에 먼저 적용하고, 문제가 생기면 이전 버전으로 되돌린다. (R-REL-1~6, R-RT-1~3)

**S5. 대화를 지켜본다.** 운영자 화면에 진행 중이거나 끝난 대화가 턴별 카드로 보인다. 카드에는 양쪽의 말과 구간별 지연 막대가 있다. 기준보다 느린 턴은 강조된다. (R-OBS-1~3, R-MON-1~3)

**S6. 턴을 되짚는다.** 카드를 열면 그 턴의 단계가 보인다. 들은 글, 말 끝 판단, 모델에 들어간 것, 도구에 보낸 것과 돌아온 것, 말한 것, 끼어들기. (R-OBS-2, R-MON-4)

**S7. 끝난 대화가 정리된다.** 대화가 끝나면 요약, 뽑아낸 정보, 성공 기준별 판정과 근거 턴이 붙는다. (R-EVAL-1~3)

**S8. 문제 턴을 사례로 남기고 다시 돌린다.** 운영자가 실패한 대화를 사례로 저장한다. 설정이나 정의서를 고친 뒤 저장된 사례와 가상 고객 시험을 전부 다시 돌려 전후 비교표를 본다. (R-EVAL-6~8)

**S9. 제작 에이전트에게 고치게 한다.** 운영자가 "본인 확인을 건너뛰는 문제를 고쳐 봐"라고 하면, 제작 에이전트가 정의서 수정안을 만들고 시험을 돌려 비교표와 함께 승인을 요청한다. 안전 규칙을 건드린 수정은 따로 표시된다. (R-BLD-3~6, R-REL-2~4)

**S10. 추세를 본다.** 에이전트와 버전별로 지연, 도구 실패율, 성공 기준 통과율, 사람에게 넘어간 비율을 본다. (R-MON-5)

**S11. 고객이 환불을 요청한다 (대표 시나리오).** 고객이 주문번호와 휴대폰 뒤 4자리로 본인 확인을 하고, 배송 상태를 묻고, 환불을 요청한다. 에이전트는 상품명과 금액을 읽어 주고 확인을 받은 뒤 환불을 접수한다. 금액이 10만 원을 넘으면 접수하지 않고 상담원에게 넘긴다. (R-TOOL-4~6, R-RT-6~8, R-SHOP-1~4)

## 5. 요구사항

우선순위: **필수**는 이번 목표에 꼭 들어간다. **권장**은 시간이 되면 넣는다.

### 5.1 에이전트 정의서 (R-DEF)

| 번호 | 요구사항 | 우선 |
|---|---|---|
| R-DEF-1 | 에이전트 하나는 폴더 하나로 정의된다. 역할·말투, 지식, 도구, 흐름 규칙, 검사 규칙, 평가, 시험이 파일로 나뉜다 | 필수 |
| R-DEF-2 | 정의서는 읽을 때 형식 검사를 받는다. 틀린 항목은 파일과 항목 이름을 짚어 알려 준다 | 필수 |
| R-DEF-3 | 버전마다 정의서 전체를 따로 보관한다. 운영 중인 버전은 바뀌지 않는다 | 필수 |
| R-DEF-4 | v1의 아바타를 첫 번째 정의서(`tech-trend-anchor`)로 옮긴다. v1과 같은 도구와 지시를 쓴다 | 필수 |
| R-DEF-5 | 코드를 고치지 않고 정의서만 바꿔 다른 에이전트를 띄울 수 있다 | 필수 |
| R-DEF-6 | 정의서 형식이 드라이브스루, 키오스크, 항공, 병원 업무를 담을 수 있다. 각각의 뼈대 정의서로 확인한다 | 권장 |

### 5.2 대화 런타임 (R-RT)

| 번호 | 요구사항 | 우선 |
|---|---|---|
| R-RT-1 | 글 채널: 글로 묻고 글로 답한다. 음성 합성과 영상 없이 동작한다 | 필수 |
| R-RT-2 | 음성 채널: 마이크 음성을 받아 말 끝 판단, 인식, 답변 생성, 음성 합성을 거쳐 음성으로 답한다. 영상 생성 없이 동작한다 | 필수 |
| R-RT-3 | 아바타 채널: 음성 채널에 영상을 붙인다. 요청할 때만 영상 모델을 올린다 | 필수 |
| R-RT-4 | 글·음성 채널은 여러 대화를 동시에 받는다. 아바타 채널은 한 번에 하나다 | 필수 |
| R-RT-5 | 답변을 문장 단위로 흘려보낸다. 도구를 부르면 추임새를 먼저 말한다 | 필수 |
| R-RT-6 | 정의서의 흐름 규칙과 금지 사항이 모델 지시에 들어간다 | 필수 |
| R-RT-7 | 정의서의 검사 규칙으로 문장을 소리 내기 전에 검사하고, 걸리면 거두고 다시 생성한다 | 필수 |
| R-RT-8 | 사람에게 넘기는 조건이 맞으면 넘김을 알리고 대화를 넘김 상태로 바꾼다 | 필수 |
| R-RT-9 | 끼어들기: 사용자가 말하면 재생을 멈추고, 대화 이력을 실제로 들린 데까지로 자른다 | 필수 |
| R-RT-10 | 말 끝 판단 방식(고정 침묵, Smart Turn), 인식 모델(Whisper, Qwen3-ASR), 언어, 답변 길이를 정의서와 채널 설정으로 고른다 | 필수 |
| R-RT-11 | 답을 미리 준비하는 기능은 조회 도구만 먼저 실행한다. 변경 도구는 고객의 말이 확정된 뒤에만 실행한다 | 권장 |

### 5.3 도구와 외부 시스템 연동 (R-TOOL)

| 번호 | 요구사항 | 우선 |
|---|---|---|
| R-TOOL-1 | 도구 하나는 계약서 하나로 정의된다. 입력·출력 형식, 종류(조회/변경), 제한 시간, 실패 유형, 개인정보 필드를 적는다 | 필수 |
| R-TOOL-2 | 모든 도구 호출은 게이트웨이 한 곳을 지난다. 게이트웨이가 입력 검사, 제한 시간, 재시도, 기록을 맡는다 | 필수 |
| R-TOOL-3 | 연결 방식은 더미, 재생, 실제(HTTP) 세 가지다. 에이전트 정의를 바꾸지 않고 전환한다 | 필수 |
| R-TOOL-4 | 변경 도구는 두 단계로 실행된다. 먼저 제안하고, 고객이 다음 말에서 동의한 뒤에만 실행된다. 게이트웨이가 이 순서를 강제한다 | 필수 |
| R-TOOL-5 | 같은 변경 요청이 두 번 실행되지 않는다 | 필수 |
| R-TOOL-6 | 실패 유형(찾지 못함, 권한 없음, 시스템 장애, 시간 초과, 입력 오류)을 구분해 모델에 알린다 | 필수 |
| R-TOOL-7 | v1의 조회 도구(날씨, 뉴스, 뉴스 상세, 긱뉴스, 위키백과, 지식 목록)를 계약서로 옮긴다 | 필수 |
| R-TOOL-8 | 더미는 장애와 지연을 흉내 낼 수 있다 | 권장 |

### 5.4 기록과 개인정보 (R-OBS)

| 번호 | 요구사항 | 우선 |
|---|---|---|
| R-OBS-1 | 대화마다 세션, 턴, 구간 기록을 저장한다. 구간은 말 끝 판단, 인식, 지식 검색, 답변 생성, 도구 호출, 합성, 출력이다 | 필수 |
| R-OBS-2 | 구간마다 시작과 끝 시각, 성공 여부, 가려진 입력과 출력을 남긴다 | 필수 |
| R-OBS-3 | 저장 직전에 개인정보를 가린다. 전화번호, 이메일, 주소, 주민등록번호, 카드번호, 주문번호, 이름 표현을 표시로 바꾼다 | 필수 |
| R-OBS-4 | 도구 계약서에 개인정보로 표시된 필드는 값 대신 표시로 저장한다 | 필수 |
| R-OBS-5 | 운영 대화의 음성은 저장하지 않는다. 시험 세션(동의하고 표시된 대화)과 가상 고객 대화만 음성을 저장할 수 있다 | 필수 |
| R-OBS-6 | 보관 기한이 지난 기록을 지운다. 기한은 설정값이다 | 필수 |
| R-OBS-7 | 기록 저장이 대화를 늦추거나 멈추지 않는다. 저장이 실패해도 대화는 계속된다 | 필수 |

### 5.6 평가 (R-EVAL)

| 번호 | 요구사항 | 우선 |
|---|---|---|
| R-EVAL-1 | 대화가 끝나면 요약을 만든다 | 필수 |
| R-EVAL-2 | 정의서에 적힌 항목을 대화에서 뽑아낸다 | 필수 |

## 7. 완료 조건

아래가 모두 되면 이번 목표를 달성한 것으로 본다. 각 항목은 `PLAN.md`의 확인 절차로 검증한다.

1. `tech-trend-anchor`와 `shop-support` 두 에이전트가 같은 서버에서 정의서만으로 뜬다.
2. `shop-support`가 글 채널에서 S11(본인 확인 → 배송 조회 → 환불 접수 또는 넘김)을 끝까지 수행한다.
3. 음성 채널과 아바타 채널에서 한 턴 이상 대화가 된다.
4. 대화가 끝나면 기록, 요약, 뽑아낸 정보, 성공 기준 판정이 저장되고 모니터 화면에 보인다.
5. 저장소에 개인정보 원문이 없다.
6. 가상 고객 시험 한 벌이 돌고 결과표가 나온다.
7. 제작 에이전트에게 말로 수정을 시키면 초안 버전이 생기고, 시험 → 승인 → 배포 → 되돌림이 된다. 승인 없는 배포는 거절된다.
8. v1이 그대로 실행된다.
